Q1 · choosing a model

"Which encoder should I start with? There seem to be so many, and why is it always DeBERTa?"

The catalog is long, but it sorts into a few backbone families and one default. Zero-shot classification works with any model trained on natural language inference (the MNLI, XNLI, and ANLI corpora), whatever the backbone underneath. The backbones you will meet are BERT, RoBERTa, DeBERTa, and the newer ModernBERT. We lean on DeBERTa-v3 for one concrete reason. Timoneda and Vallejo Vera (2025) benchmarked the families on political text and found DeBERTa generally ahead. RoBERTa and BART models are entirely valid and are sometimes the better fit for speed, ecosystem, or language coverage.

English, general purpose · start here
MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli — Start here. The workshop default. DeBERTa backbone, about 184M, runs on free Colab CPU.
facebook/bart-large-mnli — The original zero-shot default. BART backbone. By far the most downloaded. English.
roberta-large-mnli — The classic RoBERTa NLI model. Fast, well documented, a fine alternative to DeBERTa.
Higher accuracy or newer architecture · English
MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli — Large DeBERTa. Best English accuracy when you have a GPU.
MoritzLaurer/deberta-v3-base-zeroshot-v2.0 — Trained specifically for zero-shot, with a cleaner commercial license.
MoritzLaurer/ModernBERT-base-zeroshot-v2.0 — Newest backbone. Fast, and it handles long inputs (see Q3).
Multilingual · non-English text
joeddav/xlm-roberta-large-xnli — RoBERTa backbone, trained on XNLI across many languages.
MoritzLaurer/mDeBERTa-v3-base-mnli-xnli — DeBERTa backbone, roughly 100 languages.
MoritzLaurer/bge-m3-zeroshot-v2.0 — Multilingual and built for long documents.
Then. Once you gather roughly 300 or more hand-labels, fine-tune a base encoder (DeBERTa-v3-base or RoBERTa-base) rather than staying zero-shot. Score whichever model you pick on your own gold set with Cohen's kappa before you optimize, and pin the exact Hugging Face model ID so the result replicates. For ready-made political classifiers, look at the Political DEBATE models.
Default to remember. Begin with MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli. The backbone family matters far less than validating your choice on your own labeled data.
Q2 · coding with an AI agent

"I'm not a Python whiz. I want to code with Claude Code or Codex. How do I write these scripts, and what is Colab for if I run them with those tools?"

Claude Code, Codex, and similar tools are AI coding agents. You describe the task in plain English, for example "load this CSV, run zero-shot classification with these three labels, and save a results table," and the agent writes and edits the Python for you. You do not write it from scratch. You do read it, run it, and check that the output makes sense.

Writing the code and running the code are two separate jobs. The agent does the writing. Something still has to execute the result, with Python installed, the libraries present (transformers, torch), and ideally a GPU attached. That second job is what Colab handles. It hands you a ready-made Python environment and a free GPU in the browser, with nothing to install. Encoder inference runs roughly 10 to 50 times faster on that GPU than on a typical laptop CPU.

Two setups work well.

  1. Write with the agent, run on Colab. Have the agent produce the script on your laptop, push it to a GitHub repo or copy the cells across, then open Colab and run it on the free GPU. Colab cells also accept shell commands with a leading !, so !pip install and !python myscript.py work right inside the notebook.
  2. Write and run on your own machine. If your laptop has a usable GPU (an NVIDIA card, or Apple Silicon) the agent can run the script locally and you can skip Colab. On a CPU-only laptop, small jobs are fine and large ones are slow.

So the agent and Colab solve different problems. The agent writes the script. Colab gives you free hardware and a clean environment to run it on. If you already own a capable machine, you may not need Colab at all.

One safety rule for every setup. Keep API keys out of the script. Use Colab's Secrets panel or an environment variable. Never paste a key into a code cell.
Q3 · long text

"Can I feed long paragraphs into these encoders? Your demo examples are only 10 to 20 words."

Yes, up to a limit, and the limit is counted in tokens rather than words. A token is roughly three quarters of an English word. The classic encoders (BERT, RoBERTa, DeBERTa-v3, in base or large) accept up to 512 tokens, which is about 350 to 400 English words, a healthy paragraph. The short sentences in the demo are only for clarity. The very same pipeline call takes a full paragraph with no change.

The catch is silent truncation. When the text runs past the model's limit, the pipeline quietly drops the overflow and scores only the beginning. A 2,000-word UN speech fed in whole would be judged on its first few hundred words, and no warning would appear. Always know how long your texts are and confirm they fit.

For text longer than the limit, two clean options.

  1. Split and aggregate. Break the document into sentences or paragraphs, score each piece, then combine the scores into one document measure with a mean, a max, or a weighted sum. This is exactly how the case-study paper from Slide 14 builds a country-year measure out of paragraph-level scores.
  2. Use a long-context encoder. ModernBERT models accept up to 8,192 tokens, and bge-m3 also handles long input. These let you score a long passage in a single pass.
A good habit. Decide whether your concept lives at the sentence, the paragraph, or the document level, then score at that level on purpose. The unit you choose shapes every number downstream.
Q4 · sensitive data

"Is it okay to run analyses on sensitive or protected data on Colab?"

Treat free Colab as a third-party cloud service. Anything you upload is sent to Google's servers and processed there. For public text (UN speeches, news, public social-media posts) that is perfectly fine. For sensitive, personal, or regulated data, the honest default answer is no, at least not without clearance.

The decision is governed by your data rules, not by convenience. Three things to check before any upload.

  1. Your IRB approval and data use agreement. Many agreements forbid moving data to non-approved third-party processors. Human-subjects, personal, or health data often cannot leave approved infrastructure at all.
  2. GDPR and your institution's policy. If the data contains personal data of EU residents, uploading it to free Colab can count as an unlawful transfer to a third party. Clear this with your institution's data protection officer first.
  3. The tier of Colab. Free and Pro Colab are consumer-grade and carry no data-processing contract. Mounted Google Drive data is stored on Google. Only Colab Enterprise, through Google Cloud, offers the contractual protections regulated data usually requires.

Here is the good news, and it is the reason we spend Day 1 on encoders. An encoder runs offline. After the one-time model download, the model sits on your machine and no text ever leaves it. That makes a local encoder the strongest privacy option in this whole workshop. A generative API is the opposite, since every call ships your text to the provider.

Bottom line. Public text on Colab is fine. For sensitive data, run the encoder locally on your own machine or on institution-approved compute, de-identify wherever you can, and clear it with your data use agreement, IRB, and data protection officer before you start.
